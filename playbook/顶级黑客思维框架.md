# 顶级黑客思维框架

> 来源：Agentic-Bug-Hunter bug-bounty 方法论，结合本项目实战经验整理。
> 核心原则：普通黑客跑工具、查清单、30 分钟放弃；顶级黑客建立应用内部心智模型，问"为什么这样实现"而不是"这个端点做什么"。

---

## 一、普通黑客 vs 顶级黑客

| 维度 | 普通黑客 | 顶级黑客 |
|---|---|---|
| 方法 | 跑工具、查清单 | 建立应用内部心智模型 |
| 问题 | "这个端点做什么？" | "什么业务决策导致开发者这样实现？他们可能偷了什么懒？" |
| 耐心 | 30 分钟没进展就放弃 | 1 小时没进展才换上下文 |
| 范围 | 一个端点一个端点地测 | 一个功能一个功能地测，测功能间交互 |
| 自动化 | 过度依赖扫描器 | 扫描器只做初筛，手动深挖 |
| 漏洞类型 | 追热门（XSS/SSRF/XXE） | 找冷门（缓存投毒/业务逻辑/竞态/OAuth链） |
| 报告 | 一个洞一份报告 | 一条链一份报告，量化业务影响 |

## 二、狩猎前心智框架（4 步）

### 第 1 步：皇冠珠宝思维

在碰任何东西之前，问：

> "如果我是攻击者，只能做一件事，什么造成最大破坏？"

| 应用类型 | 皇冠珠宝 |
|---|---|
| 金融应用 | 转走资金、转账到攻击者账号 |
| 医疗应用 | PII 泄露、HIPAA 违规 |
| SaaS 应用 | 租户数据交叉、管理员接管 |
| 认证提供商 | 完整 SSO 链攻陷 |
| 电商应用 | 订单篡改、价格修改、无限积分 |
| 社交应用 | 私信泄露、账号接管、冒充发帖 |

**先找到皇冠珠宝，再找通往皇冠珠宝的路径。** 不要从"哪里有洞"开始，要从"哪里最值钱"开始。

### 第 2 步：开发者共情

像构建这个功能的开发者一样思考：

- 最简单的实现是什么？
- 凌晨 2 点疲惫的开发者会在哪里偷懒？
- 认证在哪里检查？控制器？中间件？数据库层？
- 不经过端点 A 直接调端点 B 会发生什么？
- 这个功能是复用旧的认证逻辑，还是有自己的？
- 移动端 API 和 Web 应用共享认证逻辑吗？
- 这个功能是同一个团队建的还是第三方？

**关键洞察：开发者不一致 = 最强证据。** 如果 9 个地方检查了认证，第 10 个没检查，那就是你的洞。

### 第 3 步：信任边界映射

```
客户端 → CDN → 负载均衡 → 应用服务器 → 数据库
  ^         ^          ^            ^
  哪里停止信任输入？
  哪里假设输入已经验证过？
```

画出完整的请求路径，在每一跳标记：
- 哪里做了输入验证？
- 哪里做了认证/授权？
- 哪里假设上游已经验证过？
- 哪里可以注入未验证的输入？

**信任边界的缺口就是漏洞。**

### 第 4 步：功能交互思维

- 这个新功能是复用旧的认证，还是有自己的？
- 移动端 API 和 Web 应用共享认证逻辑吗？
- 这个功能是同一个团队建的还是第三方？
- 功能 A 的输出会被功能 B 使用吗？
- 两个功能之间有没有隐藏的状态共享？

**新功能 = 未审查。** 最近 30 天上线的功能安全成熟度最低。

## 三、顶级黑客的 7 条规则

### 规则 1：猎功能，不猎端点

> "Hunt the feature, not the endpoint."

- 找到服务一个功能的所有端点
- 然后测试它们之间的**交互**
- 端点 A 可能没问题，端点 B 可能没问题，但 A→B 的交互可能有洞

**示例**：单独看 `/api/users/{id}`（GET）没问题，单独看 `/api/users/{id}`（PUT）也没问题，但 GET 返回的数据可以直接喂给 PUT，导致越权修改。

### 规则 2：授权不一致就是你的朋友

> "Authorization inconsistency is your friend."

- 如果应用在 9 个地方检查了授权，第 10 个没检查，那就是你的洞
- 找授权检查的模式：哪些端点有 `@PreAuthorize`，哪些没有？
- 找认证中间件的覆盖范围：哪些路径在白名单里？

### 规则 3：新 = 未审查

> "New == unreviewed."

- 最近 30 天上线的功能安全成熟度最低
- 新功能通常赶工期，测试不充分
- 关注 changelog、release notes、最近的部署

### 规则 4：二阶思维

> "Think second-order."

- **二阶 SSRF**：URL 存在数据库里，被 cron job 定时获取
- **二阶 XSS**：存储时是干净的，在管理后台渲染时不安全
- **二阶 SQLi**：数据第一次插入时转义了，从数据库读出后使用时没转义
- **二阶命令注入**：输入被存到配置文件，后续脚本读取配置文件时执行

**问自己：这个数据之后会被谁使用？怎么使用？**

### 规则 5：跟着钱走

> "Follow the money."

- 任何涉及支付、账单、积分、退款的功能，开发者最容易在安全上偷懒
- 这些功能业务逻辑复杂，边界条件多
- 竞态条件、并发问题、整数溢出在这些地方最常见

**优先测试：支付、转账、充值、提现、积分、优惠券、退款。**

### 规则 6：移动端用的 API

> "The API the mobile app uses."

- 移动端应用通常调用更旧或不同的 API 版本
- 同一家公司，不同的攻击面，更低的安全成熟度
- 移动端 API 可能缺少 Web 端有的认证检查
- 移动端 API 可能有不同的速率限制

**方法**：抓包移动端，对比 Web 端 API，找差异。

### 规则 7：对比找洞

> "Diffs find bugs."

- 对比旧 API 文档 vs 新 API 文档
- 对比移动端 API vs Web API
- 对比免费用户能请求的 vs 付费用户响应中得到的
- 对比文档说的 vs 实际行为

**差异就是漏洞的线索。**

## 四、顶级黑客心智检查清单

开始狩猎前，确认：

```
[ ] 我知道这个应用的核心商业模式
[ ] 我作为真实用户用了这个应用 15+ 分钟
[ ] 我知道技术栈（语言、框架、认证系统、缓存）
[ ] 我读过这个项目至少 3 份公开报告
[ ] 我有 2 个测试账号（攻击者 + 受害者）
[ ] 我找到了皇冠珠宝（最值钱的目标）
[ ] 我画出了信任边界
[ ] 我列出了所有功能及其交互
```

## 五、AI 辅助狩猎的提示词模板

当使用 AI 助手辅助狩猎时，用这些提示词形状：

```
"给定这个功能，列出 10 个最可能的信任边界错误。"
"哪些兄弟路由、方法或角色是我接下来应该测试的？"
"一个疲惫的开发者可能在这里复用了什么？"
"能证明影响的最小可复现请求是什么？"
"什么证据会把这个降级为 N/A？"
```

**AI 可以排序假设，但只有真实请求/响应差异和跨账号对比才能提升发现。**

## 六、本项目实战中的思维框架应用

| 思维框架 | loop3 实战应用 | 结果 |
|---|---|---|
| 皇冠珠宝思维 | 先定位转账功能（资金操作），再找通往转账的路径 | VULN-03 SECRET_KEY→CSRF→转账链 |
| 开发者共情 | 问"开发者为什么用 HMAC-SHA256 做 CSRF 令牌？"→ 发现密钥泄露即可伪造 | CSRF 令牌完整伪造 |
| 信任边界映射 | 画出 /debug→SECRET_KEY→CSRF 校验→转账 的信任链 | 发现 /debug 无认证是信任边界缺口 |
| 二阶思维 | Shiro deleteMe 不是有效 oracle → 换用外带 oracle + /proc 证据 | C1 Shiro RCE 突破 |
| 跟着钱走 | 优先测试转账、积分、优惠券 | 发现并发竞态可把余额扣成负数 |
| 对比找洞 | 对比加固版 vs 原版，对比有 token vs 无 token | 发现 12 项加固判定 + 残余绕过 |

## 七、避免的思维陷阱

```
陷阱 1：工具驱动 — "nuclei 扫到什么就测什么"
  → 应该是目标驱动：先定皇冠珠宝，再选工具

陷阱 2：端点驱动 — "一个端点一个端点地测"
  → 应该是功能驱动：测功能内和功能间的交互

陷阱 3：单洞思维 — "找到一个洞就写报告"
  → 应该是链化思维：找到 A 后继续找 B 和 C

陷阱 4：理论可行 — "这个应该可以利用"
  → 必须有真实 PoC 和可量化的影响

陷阱 5：过度自动化 — "全靠扫描器"
  → 扫描器只做初筛，手动深挖才是关键

陷阱 6：追热门 — "大家都找 XSS/SSRF"
  → 找冷门：业务逻辑、竞态、OAuth 链、缓存投毒

陷阱 7：浅侦察螺旋 — "一直在 403/401 上打转"
  → 5 分钟没进展就换目标，不要在死胡同里耗
```
