## 〇、先分流：这活儿能不能投稿？（**来自 loop3 C1/C2 实战**）

> **写在最前面**：C1/C2 写得再好，**也不能直接投漏洞盒子**。原因不是质量不够，是**性质不对**。
> 先分流再填模板，否则填一晚上发现投不了，纯浪费。

### 0.1 两条路线的判定与填法对照

| 维度 | **A 路：可投稿的发现型漏洞** | **B 路：CVE 复现 / 能力建设** |
|---|---|---|
| **是什么** | 你**自己**发现的问题：越权、业务逻辑缺陷、组件的**未公开**新用法、本组织系统的独有缺陷 | 已公开 CVE 的复现、已知漏洞的靶场练习、能力建设笔记 |
| **判定标准** | 厂商/CVE 库查不到对应编号，危害来自**该目标自身的业务实现** | 有明确 CVE 编号且**已公开披露**（如 CVE-2016-4437、CVE-2017-12615） |
| **能投稿吗** | **能**，走漏洞盒子众测流程 | **不能**，非原创发现，提交会被判重复/无效 |
| **风险等级栏** | 按 §6 严格对照 rubric 填 **高/中/低** | **不填等级**；笔记里按"练习难度"自评，别跟漏洞等级混 |
| **影响资产栏** | 填**真实目标**完整 URL + 参数 | 填**本地靶场地址**（`http://127.0.0.1:18081/`）+ 容器名 |
| **测试环境栏** | 填真实浏览器版本 + 账号类型 | 填**镜像/版本 + 部署形态**（`vulhub/shiro:1.2.4`，standalone jar） |
| **根因栏** | 写**该目标的代码/配置**为什么错 | 写**上游产品的配置层根因**，并声明"这是 Vulhub 教学环境的刻意配置" |
| **必写的声明** | 无 | **性质声明**（见 §0.2） |
| **复现率** | 写区间（`≥95%（5/5）`），禁 100% | 同左，另附**阴性清单** |
| **收尾** | 保留证据留档 | **必写清理证明**（见 §9.3） |

### 0.2 性质声明模板（B 路必抄，放报告正文最前面）

C1 笔记里的原文写法，直接沿用：

```
【性质声明】
本篇是 CVE-2016-4437 的复现记录，不是「漏洞盒子可提交的发现型报告」。
- 该 CVE 已公开、已分配编号、已官方修复。
- 本篇用途：掌握「默认凭据 + 不安全反序列化」这条配置层根因的分析路径，
  以及积累可复现的证据链组织方式。
- 不得当作原创发现提交给任何赏金平台。
- 本轮未验证：各版本的具体修复边界（哪个 patch 版本彻底消除默认密钥）未验证，
  下文只写本轮实测到的 1.2.4 行为。
```

> **「本轮未验证：……」这一句是 AI 不会写的**。C1、C2 两篇**都在开头写了未验证项**
> （C1：Shiro 修复边界未验证；C2：Tomcat patch 版本未验证）。
> 详见 §7.3 量化判据第 5 条 —— **报告里出现 ≥1 处显式未验证声明，是真人记录的第一特征**。

### 0.3 从 B 路迁到 A 路需要什么

复现笔记不能投稿，但**它是投稿前的必经训练**。真要投的时候，还差三样：

1. **陌生目标上的独立定位**（不是照 CVE 编号打，是自己找到问题）
2. **该目标自身的业务逻辑根因**（不是"上游组件默认配置"）
3. **不重复**：提交前必须核查漏洞盒子/厂商 SRC 是否已有同类报告

> 能力等级严格对照 `security/learning/能力矩阵-赏金能力记分板.md` 的 0–5 rubric：
> **3 级 = 在没给漏洞位置的陌生本地靶场独立定位并稳定复现**；
> **"证明阴性 / 识别防护"最多记 1 级**；**未达 3 级不得标 3**。
> C1/C2 属于**照 CVE 编号复现**，按 rubric 定义属 **2 级**（"能照教程/Poc 在已知漏洞靶场复现"），
> **不得因为"打通了"就抬到 3 级**。

```
【漏洞类型】【目标域名或IP】【接口/功能路径】【参数名】存在【一句话问题】

风险等级：【高危/中危/低危】
影响资产：【完整URL，例 https://www.example.com/api/order/detail，参数 orderId】
测试环境：【Chrome 版本 + Windows 版本；普通注册账号/未登录/管理员账号】

漏洞简述：
测试【哪个功能】的时候发现，【接口】接收【哪个参数】，后端没有【做什么校验/怎么处理】，【怎么改参数】之后服务端直接【返回了什么/执行了什么】，可以【实际能做到的事，一句话】。

复现过程：
1、【前置：注册并登录普通账号A，账号id/手机号为xxx；准备账号B】
2、【访问哪个页面/功能，抓包得到请求：GET/POST 路径?参数=正常值，此时返回自己的数据/正常结果】
3、【把哪个参数改成什么值（他人id/0.01/单引号payload/...），重放数据包】
4、【服务端返回了什么：贴关键响应字段/状态码/页面变化】

【贴能证明漏洞的响应行/字段，敏感数据中间打码，如手机号 138****1234；命令执行贴回显，SQL注入贴 version()/user() 结果即可，禁止拖库】

1、【在哪个接口、在哪一步、做什么校验，例：查询订单前校验该订单归属当前登录用户】
2、【不要用前端传入的什么，改为从 session/服务端取什么】
3、【加日志/限流/二次确认等可落地措施】

```

### 1.1 分类型扩展栏 · A：反序列化 / 加密凭据类（**来自 loop3 C1 实战**）

> 普通七段装不下「密钥从哪来」「凭什么说打通了」这两件事，**C1 笔记证明这两件是审核最容易打的点**。
> 在上面的模板里，**「漏洞简述」之后**插入以下三栏。

```
密钥/凭据来源：【公开源码默认常量（如 XXX）/ 从目标配置读到的值 / 未知——不确定就不要写】
  来源自证：【用什么办法证明这个密钥确实对得上。例如：用该密钥解密目标自己签发的同类凭据，
             得到合法结构头 aced0005，长度 1308 B；能解 ⇒ 密钥对得上。
             —— 不要写"密钥看着像默认值"，那是猜，不是证。】

判定依据（成功与否）：
  【列出实际采用的判据，按可靠性排序，并写明每条命中的具体结果】
  1.【首选：出网回调 / 外带收到请求，路径内嵌真实命令输出】
  2.【次选：目标主机进程表采样到拉起的子进程】
  3.【兜底：服务端日志出现解密相关异常，如 BadPaddingException —— 有异常才说明这一步被执行过】
  ⛔ 不采用的判据（**必须写出来，并说明为什么不采用**）：
  - 【响应标志 deleteMe=true —— 实测对正确密钥/错误密钥/垃圾密文/超长垃圾一律返回 true，零区分度】
  - 【响应时间 sleep 计时 —— Runtime.exec() 异步，JVM 不等子进程结束就返回，delta 实测 -0.002/+0.008/-0.003 秒，
     三条真成功的链全被误判为 executed:false】

独立证据交叉（**至少两条，且性质不同**）：
  A. 证明【数据能流出】：【OOB 收到含真实命令输出的请求原文】
  B. 证明【动作真发生】：【进程表 / 日志调用栈】
  ——只有 A 时可能是回显伪造；只有 B 时证明不了数据外流。两条齐了才算闭环。
```

> **这一栏的价值在于「不采用的判据」**。C1 笔记 §2.4 整节都在讲这个：
> 「**一个错误的判据不只是「结论不准」，而是会让你把真漏洞当阴性丢掉。**」
> 报告里写清楚"我试过 X，它不行，因为 Y"，比只写"我成功了"可信得多。

### 1.2 分类型扩展栏 · B：文件上传 / 落盘类（**来自 loop3 C2 实战**）

> 同样插在「漏洞简述」之后。**C2 笔记 §4.3 记了一处硬伤**：汇报文本写"上传前 404"，
> 原始证据实测是 **200**（文件此前已存在）。**这种出入 reviewer 一抓一个准。**

```

    PUT /xxx.jsp 被拦。差一个斜杠，从 RCE 变成 403。报告里漏了这个细节，
    等于让审核白试一轮。】
  上传文件名：【xxx.jsp（含生成规则）】  文件内容性质：【只读命令探测，不写文件、不反弹 shell】
  实际执行的命令逐条列出：【id / whoami / hostname / pwd / cat /etc/hostname —— 全部只读】

落地证明（三步，缺一不可）：
  1.【上传前 GET 该路径的基线状态：HTTP 404（期望）/ 或如实写实测值】—— C2 实测此处曾为 200，如实记录
  2.【上传后：PUT 响应状态码 + 目标机 ls -l 结果（文件名/字节数/属主）】
  3.【访问该文件：GET 200，贴回显原文，逐段标注每个字段的含义】

清理证明（**B 路必写，A 路涉及时也写**）：
  【不要写"我删了"。C2 原话："我删了"不是证据，"我删了并核验过"才是。】
  1.【删除动作，并说明 HTTP DELETE 是否可用（实测 DELETE /xxx.jsp → 405，.jsp 归 JspServlet 管）】
  2.【删除后复核：再次 GET 全部测试文件 → 全部 404】
  3.【环境终态：容器 state=exited, exit_code=143(SIGTERM 正常停止), ports={}】
```

## 五、证据与文件规范

- 证据目录：`security/learning/_evidence/`（学习）/ `security/reports/evidence/`（平台实战）
- 命名：`verify-编号-类型-YYYYMMDD-HHMM.json`、`verify-编号-类型-截图01.png`、`poc-编号-类型.py`
- 每个结论引用证据写**完整文件名 + sha256**，不用"见附件"一笔带过
- 阳性、阴性**双清单**：测了但没成功的也要留证（N-xx），证明覆盖面、避免重复劳动
- 复现率写区间（如 ≥95%：30 并发 3/3 轮出现 + 1 轮 26/30 未触发），**禁止写 100%**
- 请求/响应包用代码块原样保留，不手工"美化"，保证可重放
- 截图要求：完整请求包 + 关键响应包同框或分两张，关键参数/字段高亮；越权类必须有"当前身份"与"他人数据"对比

### 5.1 增补规范（**来自 loop3 C1/C2 实战**）

- **sha256 由归档者独立重算**，不采信笔记正文里转录的值（C1/C2 均为归档时独立重算）
- **被推翻的证据文件保留不改**，在正文以"判定 oracle 失效导致的无效结论"标注 —— C1 笔记明确写：「**该原始文件保留不改**（已归档证据不重写）」
- **作废结论要单列一节**，写清"作废范围"：C1 的做法是「仅指该文件的密钥爆破结论；**C1 本身不作废**」
- **工具缺陷导致的污染要写进笔记**：C1/C2 都记了同一条 —— `kali-run.py` 会在 stdout 末尾追加 `{"rc":...,"stdout_len":...}`，若下游脚本"取第一行"而目标输出不带换行，这段 JSON 会被拼进数据
- **风险项闭环后改写为"已修复"**，别让过期告警一直挂着（C2 §4.7 即此例）
- **每篇末尾附"引用存在性自检"**，给出可复跑命令与期望输出（`total=21  missing=0` 这种）

## 六、风险评级速查（详见《书写规范》第二节）

| 等级 | 典型情形（满足其一） |
|---|---|
| 高危 | getshell/命令执行；SQL 注入可写库；批量拿身份证/银行卡/密码；支付可 0 元购/任意退款 |
| 中危 | 越权看一般隐私（手机号/地址/订单）；盲注/报错注入；任意文件读配置/源码；验证码绕过、会话固定等认证缺陷 |
| 低危 | 反射 XSS、路径/版本信息泄露、弱口令无实质危害、CSRF/JSON 劫持等需交互且危害有限 |

> 拿不准就低不就高，并在报告里如实写危害边界；等级评错是打回重灾区。

### 6.1 两条评级纪律（**来自 loop3 C1/C2 实战 + 记分板 rubric**）

1. **别把"可达"当"危害"。** C1 笔记「不是什么」一节写得清楚：
   「不是『Shiro 有反序列化就等于 RCE』——**必须同时满足**：默认密钥 + classpath 有可用 gadget 链」。
   C2 同理：「不是『Tomcat 能 PUT 就是漏洞』—— 默认 `readonly=true`」。
   **报告里必须写"不是什么"，否则等于承认可达性即高危。**
2. **能力等级 ≠ 漏洞等级，两套 rubric 别混。** 漏洞等级按上表高/中/低；
   能力等级按 `security/learning/能力矩阵-赏金能力记分板.md` 的 0–5 rubric：
   - **未达 3 级不得标 3**
   - **"证明阴性 / 识别防护"最多记 1 级**
   - 每条等级必须指出**对应产物文件**
   - C1/C2 属于**照 CVE 编号复现**，按 rubric 属 **2 级**（"能照教程/Poc 在已知漏洞靶场复现"），
     **不得因为"打通了"就抬到 3 级** —— 3 级要求"在**没给漏洞位置**的陌生本地靶场独立定位"

### 7.2 反例：一眼 AI 的句式（命中就改写）

| # | AI 腔句式（典型特征） | 怎么改成真人写法 |

### 7.3 量化判据（写完拿计算器量一遍）

| # | 判据 | 阈值 | 怎么量 |
|---|---|---|---|
| 1 | 句子长度标准差 σ | **≥ 8 字** | 按句号/分号切句，记每句字数，算 σ；σ < 8 = 匀速机读感 |
| 2 | 短句-长句交替次数 | **≥ 3 处** | 找「≤10 字的句子后面紧跟 ≥40 字的句子」的模式 |
| 3 | 具体值密度 | **每 100 字 ≥ 1 个** | 具体值 = 数字/版本号/文件名/状态码/字节数/毫秒/端口/IP |
| 4 | 段落长度离散度 | **最长段 ÷ 最短段 ≥ 3** | 各段字数极差；比值接近 1 = 分段是按字数凑的 |
| 5 | **显式未验证声明** | **≥ 1 处** | 搜「未验证」「未实测」「不确定」「没有验证」。**AI 几乎从不主动认领盲区** |
| 6 | 自我纠错记录 | **≥ 1 处** | 搜「一开始」「最初」「原先」「后来发现」。真人必留纠错痕迹 |
| 7 | 反向对照句 | **≥ 2 处** | 搜「不是…是…」「不等于」「≠」。C1/C2 两篇都在「不是什么」一节用 |
| 8 | AI 高频词命中 | **= 0** | 搜：综上所述 / 由此可见 / 该漏洞本质上 / 存在极大安全隐患 / 一旦被利用将 / 值得注意的是 / 全面系统 |
| 9 | 加粗密度（提交版） | **≤ 3 处** | 提交框是纯文本，加粗没意义；多说明在排版不在讲证据 |
| 10 | 证据引用完整度 | **100% 结论有出处** | 抽查 5 个结论，逐个回溯到请求包/响应包/文件 sha256 |

> **判据 5 是最重要的一条。** C1 笔记开头：「本轮**未验证**：Shiro 各版本的具体修复边界……**未验证**」；
> C2 笔记同样有一句「本轮**未验证**：Tomcat 各版本的具体修复边界」。
> **一个从头到尾声称"全都验证过了"的报告，多半是编的** —— 真测过的人一定知道哪块没测。

## 八、反序列化类填写指引（**来自 loop3 C1 实战**）

> 适用于：Shiro rememberMe、Fastjson/Jackson、WebLogic T3 等**靠密钥/序列化落地**的漏洞。
> C1 笔记原文结构，见 `security/learning/cve/C1-SHIRO-2016-4437-rememberMe反序列化默认密钥.md`
> （sha256 `625b312fc14c07e4551508b39a6250f3fa34baf70ffa55523514a2172df3d89b`）。

### 8.1 密钥来源：三个问题必须答全

| 问题 | 写法 | C1 实测答案 |
|---|---|---|
| **密钥从哪来的？** | 三选一，写死 | 公开源码常量 `kPH+bIxk5D2deZiIxcaaaA==`（`AbstractRememberMeManager.DEFAULTCIPHERKEY`） |
| **配置有没有覆盖它？** | 贴反编译结论 | `cookieRememberMeManager()` 直接 `new CookieRememberMeManager()`，**未调用 `setCipherKey()`** |
| **凭什么说它对得上？** | 必须自证 | 用该密钥解密**本端自己签发**的 cookie → 得到 magic `aced0005`，长度 1308 B |

> C1 原话：「**第 2 条旁证很关键**：如果密钥是猜的/爆破的，解密自己 cookie 不会恰好得到合法序列化流头。
> **能解 ⇒ 密钥对得上。**」
>
> ⚠️ **不要写"密钥看着像默认值"** —— 那是猜。也不要把爆破结论当发现，
> C1 的教训是：爆破结论因**判据失效**而整条作废（`t7-c1-bruteforce-out.txt` 保留不改、正文标注作废）。

### 8.2 解密成功判据：优先级表

| 优先级 | 方法 | 判据 | C1 实测 |
|---|---|---|---|
| **1** | **外带（OOB）** | 回调收到且内容内嵌真实命令输出 | 路径含 `uid=0(root)` + 容器 ID 前缀 |
| **2** | **主机进程表** | 采样到 gadget 拉起的子进程 | `FOUND_PROC pid=1279 cmd=[sleep 10 ]`，46 次采样命中 |
| **3** | **服务端日志** | 出现 `BadPaddingException` = **走到了解密这一步** | 日志含 `ClassResolvingObjectInputStream.<init>` |
| ⛔ **禁用** | 响应标志 `deleteMe` | **零区分度**：5 类输入（合法序列化/垃圾4字符/超长垃圾/正确密钥/错误密钥）**全返回 true** | 实测证伪 |
| ⛔ **禁用** | `sleep` 计时 | **`Runtime.exec()` 异步**，JVM 不等子进程。三条真成功的链 delta = −0.002 / +0.008 / −0.003 秒，全判 `executed:false` | 实测证伪 |

> C1 §2.4.3 原话：「『盲 RCE』**必须**用 OOB 或子进程观测判定，**不能靠时序、不能靠响应标志**。」

### 8.3 四重证据交叉（写进归档版 §4）

| 重 | 证据 | 证明什么 | C1 文件 |
|---|---|---|---|
| ① | 密钥来源自证（`aced0005`） | **密钥对得上** | `t7-c1-keycheck-out.txt` |
| ② | 反序列化落点调用栈 | **解密后确实进了 `readObject()`** | `loop3-t7-c1-logtrace-20261012.json` |
| ③ | 命令外带（OOB，含 `uid=0` + 容器 ID） | **数据能流出 + 命令真执行** | `loop3-t7-c1-oob.jsonl` |
| ④ | 主机进程表（`pid=1279 cmd=[sleep 10 ]`） | **进程真被拉起**（与③互不依赖） | `loop3-t7-c1-shiro-20261012.json` |

> **为什么③④必须两条**：C1 §4.3 原话 ——
> 「**只有 OOB 时可能是回显伪造；只有 `/proc` 时无法证明数据外流。两条齐了才算闭环。**」

### 8.4 依赖约束必须写（阴性也是证据）

| 依赖 | C1 实测版本 | 影响 |
|---|---|---|
| commons-collections | 3.2.1 | CC5 ✅ / CC6 ✅ / **CC2 ❌（需 collections 4）** |
| commons-beanutils | 1.9.2 | CommonsBeanutils1 ✅ |

> **反过来看这也是修复建议**：C1 §5.2 P1 写「移除 classpath 上的高危依赖 —— **依赖越少，可打链越少**」。
> 阴性清单（N-C01）证明失败原因是 **classpath 不匹配**，不是打法错。

## 九、文件上传类填写指引（**来自 loop3 C2 实战**）

> 适用于：CVE-2017-12615 类 PUT 上传、任意文件上传、webshell 类。
> C2 笔记原文结构，见 `security/learning/cve/C2-TOMCAT-2017-12615-PUT上传配置缺陷.md`
> （sha256 `79bb2717946a8d276f7c6e9b10ea3b31d52ba8bd7d7d5289cabeb37bbfe66d06`）。

### 9.1 配置层根因表（先证明"默认值被谁关了"）

| # | 配置项 | 本轮实测值 | 影响 |
|---|---|---|---|
| R1 | `conf/web.xml` 中 `DefaultServlet` 的 `readonly` | **`false`**（被显式写入） | PUT 被放行 —— **这是根因** |
| R2 | `conf/Catalina/localhost/` | **空** | 无上下文级覆盖 |

> C2 原话：「**Tomcat 的代码逻辑是对的 —— 是 `web.xml` 里这一行把它关了。**」
> 报告里必须区分**配置层根因**与**代码层漏洞**：
> 配置层 → 修复手段是配置 + 升级；代码层 → 才谈改代码。

### 9.2 落地证明三步（缺一步都不算实锤）

| 步 | 动作 | C2 实测 |
|---|---|---|
| 1 | **上传前 GET 基线** | 该路径 `GET` —— 记录实测值（**C2 此处曾为 200 而非预期 404，如实写**） |
| 2 | **上传后落盘** | `PUT → 201`，容器内 `ls -l webapps/ROOT/` 见文件名/字节数/属主 |
| 3 | **访问执行** | `GET → 200`，回显 `LOOP3T7C2READONLY=uid=0(root) gid=0(root) groups=0(root)|root|bb18b6fe2e26|/usr/local/tomcat` |

> **回显要逐段解读**（C2 §4.2 的做法）：`uid=0(root)` = 容器内 root；
> `bb18b6fe2e26` = 容器 ID 前缀；`/usr/local/tomcat` = 工作目录。
> **三者齐现 = 证明在目标容器内真实执行，不是回显伪造。**

### 9.3 清理证明三步（C2 §4.5 完整走了一遍）

| 步 | 动作 | 核验 |
|---|---|---|
| 1 | 删除 | 容器内 `rm webapps/ROOT/*.jsp`（**HTTP `DELETE` 不可用：`.jsp` 归 JspServlet → 405**） |
| 2 | **删后复核** | 再次 `GET` 全部测试文件 → **全 404** |
| 3 | 环境终态 | `state=exited`、`exit_code=143`（SIGTERM 正常停止）、`ports={}` |

> C2 §7 原话：「**「我删了」不是证据，「我删了并核验过」才是。**」
> C1/C2 两篇都做了隔离声明：**端口绑 `127.0.0.1` + `Binds=null` + `no-new-privileges` + 物理网卡 `curl exit 7`（拒绝）**。

### 9.4 最小化复现：payload 细节是成败关键

| 细节 | C2 实测 | 漏了会怎样 |
|---|---|---|
| **路径末尾斜杠** | `PUT /xxx.jsp/` 能绕过后缀白名单；`PUT /xxx.jsp` 被拦 | 从 RCE 变成 403，审核白试一轮 |
| 文件名唯一性 | 带时间戳+用途标记（`t7rce230826.jsp` / `t7rep230839.jsp`） | 文件残留污染下一轮基线 |
| 上传内容性质 | 只读探测 JSP，注释里写明「仅执行只读命令，不写文件、不反弹 shell」 | 审核怀疑留后门 |
| 首次编译延迟 | JSP 首次编译需时间，**宿主侧第一次 GET 返回 404、容器内 200** | 误判为未落地 |

> C2 §7 原话：「**差一个斜杠，从 RCE 变成 403。报告里没写这个细节，等于让读者白试一轮。**」

### 9.5 证据不干净时怎么办

C2 §4.3 实测踩过：**上传前路径已返回 200**（疑似上轮残留）→ 首次落盘证据被污染。

处理办法（C2 §7）：
1. **换独立文件名重测**（`t7rep230839.jsp`），带 `REPEAT_NAME` 标记排除残留
2. **如实记录出入**，不抹平：写「t7 汇报文本称 201，原始记录是 204，201 实际来自第二轮」
3. **标明哪一轮是主证据**：「本篇的『上传成功』证据以第二轮为准」
4. **原始记录保留不改**
