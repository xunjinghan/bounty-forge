## 1. 漏洞概述与等级

**一句话**：Tomcat 的 `DefaultServlet` 若被配置为 `readonly=false`，就允许通过 **HTTP PUT 方法**直接向 `webapps/` 下写入任意文件；写入 JSP 即被容器编译执行 ⇒ 未认证 RCE。

**本轮实测结果**：**未认证 RCE 成立**，命令在容器内以 **root** 身份执行，回显含 `uid=0(root)`。

**不是什么**（避免把可达性当危害）：

- **不是「Tomcat 能 PUT 就是漏洞」** —— 默认 `readonly=true`，PUT 会被拒。本轮**正是因为配置被显式改成 `readonly=false` 才成立**（§2.2）
- 不是代码层 bug —— **Tomcat 源码行为正确，是配置把安全默认值关掉了**

## 2. 原理

### 2.1 攻击链

```
PUT /<name>.jsp/  （尾部斜杠绕过后缀白名单）
  → DefaultServlet 收到 PUT（readonly=false 才放行）
  → 落盘 webapps/ROOT/<name>.jsp
  → Tomcat 检测到新 JSP → 自动编译
  → GET /<name>.jsp → JSP 执行 → 任意命令
```

### 2.2 配置层根因（本档重点）

| # | 配置项 | 本轮实测值 | 影响 |
|---|---|---|---|
| **R1** | `conf/web.xml` 中 `DefaultServlet` 的 **`readonly`** | **`false`**（被显式写入） | **PUT 被允许** —— 这是根因 |
| **R2** | `conf/Catalina/localhost/` | **空** | 无任何 host 级配置覆盖 `readonly` |

**关键点**：`readonly` 是 `DefaultServlet` 的**安全默认值**（`true` = 拒绝 PUT）。**Tomcat 的代码逻辑是对的 —— 是 `web.xml` 里这一行把它关了。** 这正是「配置层根因」与「代码层漏洞」的本质区别。

> **Vulhub 的 Dockerfile 做的事就是把 `readonly` 置 `false`**（t6 已核实用途）。**真实环境中这类错误配置通常来自：手工改 `web.xml`、某些初始化脚本、或为了「方便热部署」而放宽限制。**

### 2.3 尾部斜杠绕过（复现要点）

Tomcat 对 `PUT` 路径做后缀检查时，`PUT /xxx.jsp` 会被白名单拦下，但 **`PUT /xxx.jsp/`**（**路径末尾加一个 `/`**）可以绕过该检查，文件仍以 `xxx.jsp` 落盘。

**这是复现该 CVE 的关键技巧**：payload 必须带**尾部斜杠**。

```
PUT /t7rep230839.jsp/  →  落盘 webapps/ROOT/t7rep230839.jsp
```

## 5. 修复方案：配置层根因 + 升级路径

> **本档练的是配置层根因，不是代码层。** Tomcat 的代码逻辑**没有错** —— 是 `web.xml` 里 `readonly=false` 把安全默认值关了。**修复手段是配置 + 升级，不是改代码。**

### 5.1 配置层根因（两条）

| # | 根因 | 表现 | 修复手段 |
|---|---|---|---|
| **R1** | **`conf/web.xml` 的 `DefaultServlet` 被配置为 `readonly=false`** | **PUT 可向 `webapps/` 写入任意文件** | **恢复 `readonly=true`**（或**删除该覆写**，回到 Tomcat 默认） |
| **R2** | **JSP 自动编译 + 上传目录直接可执行**（`webapps/ROOT/` 下的 JSP 会被自动编译执行） | 上传 JSP = 直接 RCE，无需额外步骤 | 上传目录与可执行目录**分离**；关闭不必要的 JSP 自动编译 |

### 5.2 升级路径（按优先级）

| 优先级 | 动作 | 说明 |
|---|---|---|
| **P0** | **恢复 `DefaultServlet` 的 `readonly=true`** | **这是根因的直接修复**。检查 `conf/web.xml` 及 `conf/Catalina/localhost/*.xml` 是否存在覆写。**本轮实测该目录为空** —— 说明覆写来自 `web.xml` 本身 |
| **P0** | **升级 Tomcat** | CVE-2017-12615 的修复自 Tomcat 8.5.x patch 版本起陆续发布。**⚠️ 本轮未验证具体哪个 patch 版本彻底恢复 `readonly=true` 默认** —— 升级前请查阅官方 changelog 逐版确认，不要只看大版本号 |
| **P1** | **移除 `PUT` 方法支持** | 通过 `web.xml` 的 `<security-constraint>` 限制方法集合；或在反向代理层**直接禁掉 PUT** |
| **P1** | **上传目录与执行目录隔离** | 用户上传目录不应位于会被 JSP 编译的路径下 |
| **P2** | **加固部署** | 用 `no-new-privileges`、不挂宿主目录、只绑回环（本轮环境已符合） |

### 5.3 检测与加固建议

- **检测**：Web 服务器访问日志中出现**对 `webapps/` 下路径的 PUT 请求**，特别是带**尾部斜杠**的（`.jsp/`、`.jsp%2f`）—— 这是该 CVE 的特征请求形态
- **审计项**：任何生产 Tomcat 的 `web.xml` 都应检查 `DefaultServlet` 的 `readonly` 是否被改过
- **别为"方便热部署"放宽 `readonly`** —— 热部署的正确做法是用专门的部署工具，不是开 PUT

### 5.4 对本靶场（Vulhub）的说明

Vulhub 的 Dockerfile **就是故意把 `readonly` 置 `false`** 以复现该 CVE，**这是教学环境的刻意配置，不是生产实践**。真实环境中若发现 `readonly=false`，应立即恢复默认并排查**是谁改的、改了多久**（可能已被利用）。

## 7. 学习要点

1. **「能 PUT」不等于漏洞 —— 关键是默认被谁关了。** Tomcat 的 `readonly` 默认是 `true`（安全）。本轮成立**纯粹因为配置把它改成了 `false`**。**审计任何服务前先问：安全默认值是什么，现在是什么，谁改的。**

2. **复现时 payload 的细节决定成败。** 本例必须 **PUT 路径带尾部斜杠**（`/xxx.jsp/`）才能绕过后缀白名单。**差一个斜杠，从 RCE 变成 403。** 报告里没写这个细节，等于让读者白试一轮。

3. **汇报文本与原始证据必须逐字对。** 本篇归档时发现 t7 汇报的 `201` 实际来自第二轮、`baseline 预期 404` 实测是 `200`。**报告写"上传前 404"而原始记录是 200，是 reviewer 一抓一个准的硬伤。** 宁可如实写"这里有出入，以原始证据为准"。

4. **首次证据不干净时，用第二轮。** 因为上传前路径已 200（疑似残留），第一轮落盘证据被污染。**换成有独立文件名和 `REPEAT_NAME` 标记的第二轮**，证据链立刻干净。**这是排除干扰的通用手法。**

5. **CVE 复现笔记 ≠ 原创漏洞报告。** 本篇明确标注性质 —— 练的是**配置层根因的定位方法**和**复现路径**，不是拿去当赏金提交。

6. **污染环境的收尾必须闭环到"能证明干净"。** 删完文件再 GET 一遍确认 404，才叫收尾完成。本轮 3 个 JSP 全删 + 全 404 + 容器停止 + `exit_code=143`（正常 SIGTERM）—— **"我删了"不是证据，"我删了并核验过"才是。**

7. **风险项闭环后要写「已修复」，别让过期告警一直挂着。** t7 报告把 tomcat compose 缺 hostIP 标成 **RISK_001 高危地雷**，但 range-admin 在 t6 期间**已修为 `127.0.0.1:18082:8080`**（82 B / sha256 `7e29e11e…`）。**报告里的未闭环风险会误导下一个人重复排查、甚至重复修复。** 本篇 §4.7 已更正为**已修复**并附实测佐证（物理网卡 exit 7）。

8. **⚠️ 工具缺陷会静默污染数据：`kali-run.py` 会在 stdout 末尾追加 `{"rc":...,"stdout_len":...}`。** 若下游脚本「取第一行」而目标输出**不带换行**，这段 JSON 会被拼进数据。**铁证**（混进了 shiro 容器日志）：

   ```
   A cookie header was received [rc": 0, "stdout_len": 3884, "stderr_len": 0}] that contained an invalid cookie
   ```

   中间那段 `{"rc": 0, ...}` 明显不属于 Shiro 日志格式 —— **是工具注入的**。**规避**：按目标格式（如 base64 字符集）正则取**最长串**，或用 `kali-fetch-bin.py` 取二进制。**本条卡了 hunter-web 约 15 分钟，且会把排查方向带偏**（让人以为是 Shiro 的 cookie 解析问题）。
