# 漏洞笔记：登录态访问 GET / 稳定 500（sqlite3.Row 没有 .get()）

- **编号**：VER-10（来源 HUNT-10，t5 判定 confirmed；另对应旧编号 BUG-01）
- **靶场**：target-site-lab `http://127.0.0.1:8095`（本机授权练习环境）
- **危害等级**：低危（Low，可用性缺陷；不泄露机密）
- **CWE/OWASP**：CWE-248（Uncaught Exception）＋ CWE-704（Incorrect Type Conversion or Cast，行对象被当 dict 用）；OWASP Top 10 2021 **A04:2021 Insecure Design（错误处理与可用性）**
- **CVSS-like**：4.0（AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:N/A:L）
- **复现率**：12/12 登录态 500（alice/demo/admin 各 4 次），4/4 匿名 200
- **代码位置**：`target-site-lab/app.py:509-515`（`index`，关键行 511-513）

---

## 1. 漏洞概述

已登录用户访问首页 `GET /` **100% 返回 500**；同一路径匿名访问返回 200。原因是 `current_user()` 返回的是 `sqlite3.Row` 对象，而代码对 `(row or {})` 调用 `.get("username")`——`sqlite3.Row` 支持下标与 `keys()`，但**没有 `.get()` 方法**，于是抛 `AttributeError`，被通用异常处理兜成 500 页。

影响：任何登录态账号（含 admin）都点不开首页，登录后所有"回首页"的引导路径全部撞 500。这是**可用性/功能缺陷**，本身不泄露数据（错误页是通用的，不吐堆栈），但它会污染测试基线——自动化工具在登录态下遍历站内链接时会把首页记为异常，干扰后续判定。

---

## 2. 原理（代码层根因）

```python
# target-site-lab/app.py:509-515
conn = get_db()
try:
    self.html(200, page("靶场", body,
                        (self.current_user(conn) or {})            # L511-512
                        .get("username")))                          # L513 ← Row 没有 .get
finally:
    conn.close()
```

对照 `current_user()`（`app.py:370-377`）：它用 `conn.execute(...).fetchone()` 取行，成功时返回 `sqlite3.Row`。因此：

- **匿名**：`current_user()` 返回 `None` → `None or {}` 得到 `{}`（真 dict）→ `.get()` 正常 → 200。
- **已登录**：返回 `sqlite3.Row` → `row or {}` 得到 `row`（Row 为真）→ `.get()` 抛 `AttributeError` → 500。

这是典型的"两分支返回类型不一致"缺陷：`None` 分支与 `Row` 分支走的是同一句代码，只有一处类型支持 `.get()`。

日志佐证（挖掘与侦察阶段均记录到）：`lab_errors.log` 记 `app.py:513 AttributeError: 'sqlite3.Row' object has no attribute 'get'`。

## 5. 修复方案

### 代码级（P0，落到 `app.py:511-513`）

把行对象统一转成 dict，或统一用"存在性判断 + 下标取值"：

```python
# 改法一（最小改动）：Row 显式转换
user = self.current_user(conn)
username = dict(user)["username"] if user else None
self.html(200, page("靶场", body, username))

# 改法二：用 keys() 判断后下标取值（不复制对象）
user = self.current_user(conn)
username = user["username"] if user and "username" in user.keys() else None
```

更彻底的做法是**让取用户信息的接口返回类型统一**：`current_user()` 内部直接 `return dict(row) if row else None`，从根上消除"两分支两种类型"的坑（同时要检查其它调用点是否依赖 `sqlite3.Row` 的下标行为，`dict()` 转换后下标依旧可用）。

### 纵深防御

- **全局异常兜底**：`do_GET`/`do_POST` 外层统一 `try/except Exception`，记录日志并返回通用错误页（本项目已这么做，未泄露堆栈——这是正确做法，保持）。
- **冒烟用例**：把"每个路由 × {匿名, 普通用户, admin} 三种身份"的状态码矩阵纳入回归，500 一律失败。本例在任何有冒烟测试的项目里都会第一轮被抓出来。
- **日志告警**：`lab_errors.log` 出现同类 AttributeError 立即告警（同一异常重复 11 条说明没人在看）。
- **类型注解**：给 `current_user()` 标注返回类型 `Optional[Dict[str, Any]]`，让 IDE/静态检查提前发现问题。

## 7. 学习要点

- **考什么思路**：**同一条代码路径的两种返回类型**是最容易被漏的缺陷模式。看到 `(x or {})` 这种"兜底写法"，先问一句"x 的真实类型是什么、它支持后续调用的方法吗"。
- **为什么容易被判成"不是安全漏洞"**：它不影响保密性与完整性，只影响可用性（CWE-248 类）。但它是**测试基线污染源**：登录态爬虫把首页记为 500，会让后续所有"登录态攻击面"结论失真。所以依然要记录并修，只是等级定 Low。
- **同类变体**：
  - `cursor.fetchone()` 返回 `None` 或 tuple，代码对两者用同一套下标访问（`row[0]` 可用，`row["k"]` 不可用，反之亦然）。
  - `dict` 与 ORM 对象混用（`.get()` 与属性访问混写）。
  - 异步接口返回 `None` 被当 awaitable。
  - 空集合与 `None` 的兜底写法不一致（`or {}` / `or []` 混用导致类型漂移）。
- **写报告要点**：可用性缺陷也要给**完整矩阵证据**（三种角色 × 次数），并说明它为什么值得修（基线污染、用户体验、SLA），而不是简单甩一句"500 了"。
