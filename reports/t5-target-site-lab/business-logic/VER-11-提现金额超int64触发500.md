## 1. 漏洞概述

`/wallet/withdraw` 只校验 `amount > 0`，**没有上限**。当 `amount = 9223372036854775808`（2^63，超出 SQLite INTEGER 的 signed 64-bit 上限）时，绑定参数抛 `OverflowError`，未捕获 → 500。

**必须写清的边界（t5 修正）**：这**不是**资金漏洞。余额前后无变化（50486 → 50486），只是异常面。

**同时修正挖掘阶段的一处错误描述**：原报告写"`amount=1e23` → 500"是错的。实测 `int('1e23')` 抛 `ValueError` → 被 `except ValueError: amount = 0` 接住 → 走"金额无效"分支返回 **400**。两个机制必须分开写：

| 输入 | 代码路径 | 实测 |
|---|---|---|
| `amount=1e23` | `int()` 抛 `ValueError` → `amount=0` → `amount <= 0` 分支（`app.py:1068`） | **400 金额无效** |
| `amount=9223372036854775808`（2^63） | `int()` 成功 → 进入 `UPDATE` 绑定 → SQLite 抛 `OverflowError`（未捕获，`app.py:1075`） | **500** |
| `amount=9223372036854775807`（2^63−1，合法上界） | 绑定成功 → 条件更新 `rowcount=0` → "余额不足"分支 | **200 余额不足** |

## 2. 原理（代码层根因）

```python
# target-site-lab/app.py:1064-1078（节选）
try:
    amount = int(form.get("amount", "0"))
except ValueError:
    amount = 0
if amount <= 0:                       # L1068 只校验下界，没有上界
    self.html(400, ...)
    return
cur = conn.execute(
    "UPDATE users SET balance_cents = balance_cents - ?"
    " WHERE id=? AND balance_cents >= ?",
    (amount, user["id"], amount))     # L1075-1078 ← 超 int64 时绑定抛 OverflowError
conn.commit()
```

根因：

1. **缺上界校验**：只判 `amount <= 0`，没判"不超过账户余额/业务上限/数据库列上限"。业务上提现金额本应有一个明确上限（本例余额就是天然上界）。
2. **异常未兜底**：`conn.execute` 的绑定异常没有 `try/except sqlite3.Error`（或 `OverflowError`）兜底，异常冒泡到 `route()` 的通用错误处理，产生 500。
3. 通用错误处理只记录日志、返回通用 500 页（这一点本项目做得对，没泄露堆栈——见 VER-10 笔记的对照），但仍应避免出现"可被反复触发的 500"。

## 5. 修复方案

### 代码级（P1，落到 `app.py:1064-1078`）

```python
MAX_WITHDRAW_CENTS = 100_000_000          # 业务上限：100 万分（示例），按业务定义
try:
    amount = int(form.get("amount", "0"))
except (ValueError, TypeError):
    amount = 0
if amount <= 0 or amount > MAX_WITHDRAW_CENTS:      # 补齐上界
    self.html(400, page("金额无效",
        "<h1>金额无效</h1><p>提现金额必须大于 0 且不超过上限。</p>",
        user["username"]))
    return
try:
    cur = conn.execute(
        "UPDATE users SET balance_cents = balance_cents - ?"
        " WHERE id=? AND balance_cents >= ?",
        (amount, user["id"], amount))
    conn.commit()
except sqlite3.Error:                                # 绑定/约束异常兜底，不留 500
    conn.rollback()
    self.html(400, page("金额无效", "<h1>金额无效</h1>"))
    return
```

要点：① 上界校验（业务上限或余额本身）；② 用 `int()` 后的整数范围预检（`-2**63 <= amount <= 2**63-1`）作为兜底；③ 数据库异常统一兜底为 4xx，不产生可反复触发的 500。

### 纵深防御

- **统一参数校验层**：金额类参数（`amount`、`qty`、`price`）在同一处做「类型 + 下界 + 上界」三重校验，避免每个 handler 各写一套（本项目 `qty` 在 `app.py:934` 已有上下界，是对的范式，可抽出来复用）。
- **表结构约束兜底**：给金额列加 `CHECK(balance_cents >= 0)`，把一部分非法写入挡在 DB 层。
- **错误响应规范**：4xx 用于用户输入问题，5xx 只用于真正的服务端故障；监控 5xx 速率，出现"可复现的 5xx 输入"即建缺陷单。
- **回归用例**：`amount` 取 `0 / -1 / 1e23 / 2^63-1 / 2^63 / 空` 六组，断言状态码分别为 400/400/400/200/400/400。

## 7. 学习要点

- **考什么思路**：边界值的三个方向——**下界**（0/负数）、**上界**（业务上限）、**类型上界**（语言/数据库表示范围）。开发者通常只写下界校验（`amount > 0`），上界与类型上界被漏掉。
- **两类异常的机制不能混写**：`int('1e23')` 是**解析失败**（ValueError → 走业务分支，400）；`2^63` 是**绑定失败**（OverflowError → 未捕获，500）。写报告时把两者分开，是严谨性的体现（本项正是 t5 对挖掘阶段的修正）。
- **同类变体**：
  - 数量 `qty` 超上限（本项目已修，见 `app.py:934`）。
  - 分页参数 `page/size` 无上界导致内存放大（`size=10^9`）。
  - 时间戳/ID 超范围导致下游 JSON 序列化或 SQL 绑定异常。
  - 货币计算用整数分但换算时溢出（`cents * 100` 溢出）。
- **写报告要点**：异常面漏洞要**明确写"无数据影响"**并给出库内前后值对照；只报 500 不报影响边界的报告，容易被判成噪音。
