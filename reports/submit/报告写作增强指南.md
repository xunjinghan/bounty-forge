# 报告写作增强指南

> 来源：Agentic-Bug-Hunter report-writing 方法论，结合漏洞盒子平台特点整理。
> 用途：补充现有《漏洞盒子报告模板-提交版》，提供标题公式、CVSS 速查、降级反驳话术、提交前检查清单。

---

## 一、最重要的一条规则

> **永远不用"可能"、"也许"、"理论上可以"、"could potentially"、"may allow"。**
> 要么证明了，要么不写。

| 坏写法 | 好写法 |
|---|---|
| "这个漏洞可能允许攻击者访问用户数据。" | "攻击者通过修改 user_id 参数为目标用户 ID，可以访问任意用户的订单历史。我用两个测试账号确认：attacker@test.com (ID 123) 成功获取 victim@test.com (ID 456) 的订单，包括收货地址和支付方式后四位。" |
| "存在 CSRF 漏洞。" | "攻击者可以构造恶意页面，诱导已登录用户访问后，在用户不知情的情况下执行转账操作。已实测转账 5000 分成功，admin 余额从 100000 变为 95000。" |
| "可能存在信息泄露。" | "/debug 端点无需认证即可访问，返回 SECRET_KEY 明文、服务器绝对路径和当前时间。SECRET_KEY 可用于伪造 CSRF 令牌。" |

## 二、标题公式

```
[漏洞类型] in [精确端点/功能] allows [攻击者角色] to [影响] [受害者范围]
```

### 好标题（具体、影响优先）

```
IDOR in /api/v2/invoices/{id} allows authenticated user to read any customer's invoice data
Missing auth on POST /api/admin/users allows unauthenticated attacker to create admin accounts
Stored XSS in profile bio field executes in admin panel — allows privilege escalation
SSRF via image import URL parameter reaches AWS EC2 metadata service
Race condition in coupon redemption allows same code to be used unlimited times
SECRET_KEY leak via /debug endpoint allows CSRF token forgery and unauthorized fund transfer
Shiro default encryption key allows remote code execution via rememberMe cookie
Tomcat PUT method allows arbitrary JSP upload and remote code execution
```

### 坏标题（模糊、对分类员无用）

```
IDOR vulnerability found
Broken access control
XSS in user input
Security issue in API
Unauthorized access to user data
发现一个漏洞
有安全问题
```

### 漏洞盒子中文标题参考

```
[IDOR] /api/orders/{id} 越权可读取任意用户订单数据
[CSRF] 转账接口缺少 CSRF 令牌校验，可诱导用户转账
[RCE] Shiro 默认密钥导致 rememberMe 反序列化远程代码执行
[RCE] Tomcat PUT 方法可上传 JSP Webshell 导致远程代码执行
[XSS] 个人简介字段存储型 XSS，可在管理后台执行
[SSRF] 图片导入 URL 参数可访问云元数据服务
[信息泄露] /debug 端点泄露 SECRET_KEY 可伪造 CSRF 令牌
[会话固定] DVWA 会话 ID 可预测，可接管已认证会话
```

## 三、报告结构（漏洞盒子提交版）

```markdown
## 漏洞概述
[一段话：什么洞、在哪里、攻击者能做什么。具体到：端点、方法、参数、泄露数据、所需权限。]

## 漏洞详情
- 漏洞类型：[IDOR / CSRF / RCE / XSS / SSRF / ...]
- CVSS 3.1 评分：[X.X] ([严重/高危/中危/低危]) — [向量字符串]
- 受影响端点：[METHOD /path]
- 所需权限：[无需认证 / 普通用户 / 管理员]

## 复现步骤
### 测试环境
- 攻击者账号：[email / ID]
- 受害者账号：[email / ID]
- 目标：[URL]

### 详细步骤
1. [第一步操作]
2. 发送以下请求：
```http
METHOD /endpoint HTTP/1.1
Host: target.com
Authorization: Bearer TOKEN
Content-Type: application/json

{"param": "value"}
```
3. 观察响应：
```json
{"key": "value"}
```
4. [结论：响应包含受害者的私密数据]

### 预期行为 vs 实际行为
- 预期：[403 Forbidden / 拒绝访问]
- 实际：[200 OK + 受害者完整数据]

## 漏洞影响
[具体、量化的影响。什么数据、多少用户、攻击者能做什么。]
- 数据类型：[PII / 支付信息 / 内部文档]
- 影响范围：[所有注册用户 / 特定条件用户]
- 业务后果：[资金损失 / 账号接管 / 数据泄露]
- 攻击成本：[只需免费账号 / 需要 $X 订阅]

## 修复建议
[1-2 句具体修复。包含代码示例更好。]
```python
if order.user_id != current_user.id:
    raise Forbidden()
```

## 附件
[截图 / 视频 / 完整请求响应]
```

| 指标 | 值 | 权重 | 何时选 |
|---|---|---|---|
| **攻击向量 (AV)** | Network | +0.85 | 通过互联网 |
|  | Local | +0.55 | 需要本地访问 |
| **攻击复杂度 (AC)** | Low | +0.77 | 可重复利用 |
|  | High | +0.44 | 需要竞态/时序 |
| **所需权限 (PR)** | None | +0.85 | 无需登录 |
|  | Low | +0.62 | 普通用户账号 |
|  | High | +0.27 | 管理员账号 |
| **用户交互 (UI)** | None | +0.85 | 无需受害者操作 |
|  | Required | +0.62 | 受害者必须点击 |
| **范围 (S)** | Changed | 更高 | 影响浏览器/OS/其他 |
|  | Unchanged | 更低 | 只在应用内 |
| **机密性 (C)** | High | +0.56 | 所有数据暴露 |
|  | Low | +0.22 | 有限数据 |
| **完整性 (I)** | High | +0.56 | 可修改任何数据 |

## 五、严重程度决策指南

### 严重 (P1)

- 无需交互的任意用户账号接管
- 远程代码执行 (RCE)
- 可拖库/改库的 SQL 注入
- 到管理后台的认证绕过
- SSRF 到云元数据 → IAM 凭证窃取

### 高危 (P2)

- 大规模 PII 暴露（邮箱、手机、身份证、支付数据）
- 从用户到管理员的权限提升
- 带回显数据的内网 SSRF
- 影响所有用户的敏感功能存储 XSS
- 支付绕过 / 无限制资金损失

### 中危 (P3)

- 特定用户非关键数据的 IDOR
- 需受害者点击的敏感页面 XSS
- 重要但非关键操作的 CSRF
- 有努力证明的 OTP 速率限制绕过

### 低危 (P4)

- 非敏感信息泄露
- 有可用 PoC 的敏感操作点击劫持
- 有限数据的 CORS

### 严重程度自评估（每个 YES 升一级）

```
1. 暴露其他用户的 PII / 健康 / 财务数据？        → +1 级
2. 允许账号接管或权限提升？                     → +2 级
3. 无需受害者任何交互？                          → +1 级
4. 影响所有用户（不是特定条件）？                 → +1 级
5. 可远程利用，无需内网访问？                     → 高危及以上基线
```

## 六、降级反驳话术表

当平台试图降级你的漏洞严重程度时，用这些话术反驳：

| 平台说 | 你反驳 |
|---|---|
| "需要认证" | "攻击者只需免费账号，无需特殊角色或权限" |
| "影响有限" | "影响 [N] 个用户 / 暴露 [PII 类型] / $[金额] 风险" |
| "已经知道了" | "请给我报告编号 — 我搜了 hacktivity 没找到" |
| "设计如此" | "请给我说明这是预期行为的文档" |
| "CVSS 低" | "CVSS 不捕捉业务影响 — 攻击者可在 [Y] 分钟内提取 [X]" |
| "不可利用" | "这是显示受害者数据返回给攻击者会话的精确响应" |
| "只是信息泄露" | "泄露的 SECRET_KEY 可用于伪造 CSRF 令牌，已实测转账成功 — 这是完整攻击链的第一环" |
| "需要用户交互" | "只需诱导用户访问一个普通网页，无需下载或运行任何东西" |

## 七、60 秒提交前检查清单

```
[ ] 标题遵循公式：[漏洞类型] in [端点] allows [角色] to [影响]
[ ] 第一句话用 plain English 说明精确影响
[ ] 复现步骤有可复制粘贴的精确 HTTP 请求
[ ] 包含显示漏洞的响应（截图或 JSON body）
[ ] 用了两个测试账号 — 不是一个账号测自己
[ ] 计算并包含了 CVSS 评分
[ ] 修复建议是 1-2 句话（不是长篇大论）
[ ] 端点路径和参数名没有拼写错误
[ ] 报告 < 600 字 — 分类员会跳过长报告
[ ] 声称的严重程度匹配描述的影响 — 不要过度声称
[ ] 从未使用"可能"、"也许"、"理论上可以"
[ ] PoC 可从全新状态被分类员复现
[ ] 证据文件已计算 sha256 并记录
[ ] 已通过 7 问验证门
[ ] 不在"永不提交"黑名单上
```

## 八、人味写作指南

**写给人看，不是写给系统看：**

- 分类员很累。第一句就说到影响
- 用"我"不用"研究者" — 你发现的，你负责
- 短段落，步骤用列表
- 需要的话超链接相关文档

**升级语言（当赏金被降级时）：**

```
"这个漏洞不需要任何特殊权限 — 只需免费账号。"
"暴露的数据包含 [PII 类型]，受 GDPR / 个人信息保护法约束。"
"攻击者可以用简单循环自动化 — 所有 [N] 条记录几分钟内拖完。"
"这可以在外部利用，无需访问任何内部系统的网络。"
"影响等同于 [功能/数据类型] 的完整数据泄露。"
```

**避免：**

- 分类员可能不懂的行话
- 5 段解释什么是 IDOR（他们知道）
- 理论链（"可以和 X 组合..."）
- 被动语态（"据观察..."）
- 限定语言（"似乎"、"看起来"）
