## 2. 方案 A（推荐）：加固后复打 8095 · 测绕过

**动作定义**：按本轮已确认缺陷，对 `target-site-lab/app.py` 做**源码级加固**（每处改法在笔记里已给出），然后逐条复测，判定"修复是否有效 + 是否有绕过路径"。

| 练习题 | 加固点（源码位置） | 复测判定标准 | 练到什么 |
|---|---|---|---|
| A1 并发策略：把 `/order/create` 改为条件更新 | `app.py:949-955`（读校验 + 无条件扣款）→ 对齐 `app.py:1076` 写法 | 30 并发 × 3 轮，库内余额**从不为负**，且订单数 ≤ `balance // price` | 原子性验证；能证明"修复生效"而非"这次没触发" |
| A2 CSRF 覆盖：四个漏接入口补校验 | `/wallet/withdraw`、`/order/create`、`/order/status`、`/coupon/claim`（VER-02） | 无 token → 403；错 token → 403；正确 token → 200；**GET 顶级导航不再变更状态** | 防护面枚举完整性 |
| A3 令牌改造：CSRF 改为会话内随机值 | `csrf_token() = HMAC(SECRET_KEY, session)` → `secrets.token_urlsafe()` 存 sessions 表 | 页面 token **无法**由 `HMAC(SECRET_KEY, 会话 token)` 复现；跨会话 token 仍 403；密钥泄露后 CSRF 不再可推导 | 密钥体系设计判据（对应 `learning-path.md` 练习 B） |
| A4 会话销毁：`/logout` 删服务端行 | VER-04（假登出） | 登出后旧 Cookie 重放 `/home` → 302/401；`sessions` 表无该行 | 会话生命周期闭环 |
| A5 绕过对抗（**核心练习**） | 上述四处加固完成后 | 对每处加固，尝试**至少 3 类绕过思路**并给出三态结论（成功/失败/不可验证）；失败必须有对照请求说明校验位置 | 从"识别防线"升级为"对抗防线" |
| A6 `__reset` 加固 | VER-06（无认证一键删库） | 加 `HEAD` 方法判定 + 回环外的拒绝 + 二次确认后，爬虫/HEAD 不再触发重建 | 破坏性端点防护 |

**预期收获**：① 产出 6 份"修复验证用例"（赏金项目中修复验证是复现报告的第二形态）；② 把 `learning-path.md` 的 P0（攻击链闭环/证据纪律）与 P1（绕过对抗）同时推进；③ 得到一组"加固前 vs 加固后"的同靶场对照数据，这是最稀缺的学习材料。

**成本**：0 新环境。改码 + 复测 ≈ 1.5–2.5 小时（编码量小，判定标准明确）。
**风险**：改码后靶场"已不是原靶场"，需**先备份 `app.py` 并记录 sha256**（现 sha256 `d2992cd0…21b484`），保证可回退；改动期间 8091/8095 的基线判据（`lab.db` 哈希）不受影响。

## 3. 方案 B：换靶场 — Kali VM 的 DVWA / bWAPP（零下载过渡）

**动作定义**：启动既有 Kali VM（`VBoxManage startvm kali-linux-2026.2-virtualbox-amd64`），SSH `127.0.0.1:2222`（kali/kali，免密 sudo），`systemctl start apache2 mysql`，访问 DVWA（`admin/password`）与 bWAPP（`bee/bug`）。

| 练习题 | 目标漏洞类型 | 判定标准 | 补哪个空目录 |
|---|---|---|---|
| B1 文件包含（LFI/RFI） | 路径穿越 + LFI | 能读出 `/etc/passwd` 且给出 `php://filter` 类编码读取；能区分"包含成功"与"回显巧合" | `path-traversal/` |
| B2 XXE | XML 外部实体 | 用本地 DTD 发起受控回显；给出禁用外部实体后的对照 | 新增品类 |
| B3 真实 CSRF token 约束 | CSRF（带 token 的难度版） | 在**有 token** 的应用上复现 CSRF，说明 token 为何可被绕过（若不能，则说明防护为何有效） | 与 `ssrf/` VER-05 形成的对照 |
| B4 弱会话/会话固定 | 会话管理 | 给出会话固定成功的前后 `PHPSESSID` 证据 | `auth-bypass/` 补强 |
| B5 存储型 XSS 的完整危害证明 | XSS | 不止 `alert`，须证明 cookie/会话被劫持（可用本地搭的接收端） | `xss/` |

**预期收获**：把本轮"六类全阴性"的空白变成"六类有实证"，并且首次接触**带真实框架约束**的应用（DVWA 有 token、有会话、有数据库），与自研靶场的"裸接口"形成反差训练。
**成本**：VM 开机 + 起服务 2–5 分钟；每个练习 20–40 分钟。**风险**：VM 内 apache/mysql 状态未在本轮复验（t2 报告已注明），需起完先做一次基线；VM 网络需确认仅 host-only/回环可达。
**与方案 A 的关系**：可并行（A 改码复测在主链，B 在 VM 内做），但需 captain 分配人手。

## 4. 方案 C：换靶场 — Vulhub 首批 2 环境（shiro + tomcat）

**动作定义**（严格按 t2 `next-lab-plan.md` §5 步骤，不擅自扩大）：建 `D:\dsh-vulhub\` → gh-proxy 拉仓库 zip（87.7 MiB，≈7 min，后台作业）→ 首批只起 `shiro`（镜像已就位 501 MB）+ `tomcat`（≈121 MiB，≈10–12 min）→ 端口统一 `18080–18099` 且只绑 `127.0.0.1`。

| 练习题 | 目标 | 判定标准 |
|---|---|---|
| C1 Shiro rememberMe 反序列化（CVE-2016-4483 系） | 反序列化 + 密钥爆破 | 能说明"密钥硬编码 → rememberMe 可控 → 命令执行"的完整链路；在容器内执行**只读**验证命令 |
| C2 Tomcat PUT 上传（CVE-2017-12615） | 文件上传 → RCE | 上传后能取回受控输出，并给出"为什么 PUT 被允许"的配置层原因 |
| C3 每环境基线记录 | 沿用 t1 `baseline-*.json` 格式 | 镜像 digest、端口、初始凭据、重建方式、容器哈希 |

**预期收获**：真实 CVE 复现履历（最接近赏金报告形态的一份产物）；练"配置层根因"而非"代码层根因"。
**成本与硬前置**：
- 拉取合计 ≈12–25 min（按实测 199 KB/s）；仓库 zip ≈7 min。
- **Docker 数据盘迁移待 captain 亲自执行**（t2 裁决 1：迁移获批但由 captain 操作，迁移前需再向用户确认）；C 盘余量紧张（实测窗口 13.11 GB → 12.86 GB 且缓慢下降）。
- RCE 类验证已获分层授权，三条硬约束：只绑 `127.0.0.1`、容器内不得挂宿主目录、测完立即 `docker rm -f`（镜像可留）；若某环境必须挂宿主目录才能复现，须先报 captain。
- Docker Desktop「用完即关」的触发条件＝本轮 A/B/C 三档跑完；关闭会同时停掉既有 4 个 pentagi 容器（`127.0.0.1:8443/9443/5432/9187`，非本任务创建），**关闭时点需 captain 明确**。
