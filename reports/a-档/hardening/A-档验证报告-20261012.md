### 2.1 A1 · `/order/create` 条件更新（原子扣款）

**原理**：原版 `require_user` 读出的 `balance_cents` 是快照，N 个并发线程各自读到 50000 → 各自通过 `if user["balance_cents"] < amount` 校验 → 各自无条件 `UPDATE users SET balance_cents = balance_cents - ?`。读-判-写非原子，余额被扣穿。加固版改为单条 `UPDATE ... WHERE id=? AND balance_cents >= ?`，靠 `rowcount==0` 判余额不足。

### 2.5 A6 · `/__reset` 四层加固

**原理**：原版 `reset_endpoint` 只有一句 `if peer not in ("127.0.0.1","::1"): 403`，方法不限 → `curl -I`（HEAD）就能删库重建。加固版四层：① 回环来源 ② 仅 POST ③ `confirm=RESET` ④ 审计日志（`hard\app.py:1358-1387`）。

| `POST /__reset` 源地址 127.0.0.2（带 confirm） | — | **403**（`仅允许本机回环访问`） |

- **"HEAD 真的删库"不是推断，是实锤**：`loop2-verify-supplement3-20261012-201334.json` 的 `C1_orig_HEAD` 用 canary 行判定 —— `canary_before=2 → canary_after=1`、`canary_wiped=true`。这比看 HTTP 码硬。
- hard 侧同文件 `C2_hard_head_get_crawler` 五例（HEAD / GET / 爬虫 UA / img 标签 / Range 探测）全 405、`canary_before==canary_after`、`audit_lines_delta=0` —— **连审计都没记，因为压根没进到执行层**。
- 审计日志确实在写：`loop2-verify-sandbox\hard\reset-audit.log` 共 **78 行**，格式 `[2026-10-12 20:17:13] RESET peer=127.0.0.1 ua=lv-probe5/1.0`，末 6 行时间戳与 `loop2-verify-supplement5-20261012-201710.json`（20:17:10–20:17:13）对得上。
- **判定：有效，但为缓解非根除**（t2 报告 §4.2 自述一致，我复核同意）。理由见 §3.1。

### 2.6 真实 8095 的零状态变更复测

`loop2-verify-real8095-a1-20261012-201817.json`：目标 `127.0.0.1:8095`，`csrf_token_len=43`（加固特征），6 轮 × 30 并发（product_id 1 与 3 交替）→ **180 次全 400**，`bob_balance 100→100`、`orders 3→3`、`db_sha256` 前后一致、`all_400=true`、`any_state_change=false`。**未打 `/__reset`**（文件 meta 里明确写了）。这是对 A1 加固在真实靶上的独立确认。

## 3. 残余绕过路径（本轮最值钱的产出）

三态标注：**成功** = 绕过成立 / **失败** = 绕过被挡 / **不可验证** = 证据不足。

### 3.1 D1 · 跨站上下文未校验 → `/__reset` 可被 CSRF 触发 【成功 · 需处理】

- **证据**：`loop2-verify-supplement4-20261012-201557.json` 的 `D1_cross_site_reset`。
- **载荷**（裸 socket，动态 `Content-Length=13`）：
  ```
  POST /__reset HTTP/1.1
  Host: h
  Content-Type: application/x-www-form-urlencoded
  Origin: http://evil.example
  Referer: http://evil.example/poc.html
  Sec-Fetch-Site: cross-site
  Sec-Fetch-Mode: navigate
  Sec-Fetch-Dest: document
  Content-Length: 13

  confirm=RESET
  ```
- **结果**：`status=200`、`title=reset`、`canary_before=2 → canary_after=1`、`reset_triggered=true`、`audit_delta=1`。
- **同样成立的变体**：`confirm` 只放 query（无 body）→ 200 触发；`Origin: http://127.0.0.1:18096`（同源）→ 200；**完全不带 Origin**（curl 风格）→ 200。
- **根因（源码位置）**：`hard\app.py:1358-1375`。四层校验依次是 `client_address` 回环、`self.command != "POST"`、`form.get("confirm") != "RESET"`、审计 —— **没有任何一层读 `Origin` / `Referer` / `Sec-Fetch-Site`**。回环校验看的是 TCP 源 IP，不是"谁发起的"。
- **影响边界（必须说清，别夸大）**：这条只在**攻击者与靶场同机**（或攻击者已在回环上）时成立 —— 因为 ① 层仍然要求 `client_address ∈ {127.0.0.1, ::1}`。所以真实场景是：**受害者在本机浏览器打开恶意页面 → 该页面自动提交表单 → 复位成功**（受害者浏览器从 127.0.0.1 发起）。远程攻击者打不到。
- **修复方向**：加 ① 层之外的上下文校验 —— 要求 `Origin` 必须是 `http://127.0.0.1:<port>`（缺失 Origin 也拒绝，别用"没带就放过"），或干脆给复位加一个启动时生成的一次性 token（`--reset` 参数路线，t2 报告 §4.2 提过但当时没采纳）。

### 3.2 D2 · 方法覆盖头 【失败 · 阴性留证】

- **证据**：`loop2-verify-supplement4-20261012-201557.json` 的 `D2_method_override`。
- 四种尝试全部 **405**、`reset_triggered=false`、`audit_delta=0`：
  | 用例 | 状态 |
  |---|---|
  | `GET /__reset` + `X-HTTP-Method-Override: POST` | 405 |
  | `GET /__reset` + `X-Method-Override: POST` | 405 |
  | `GET /__reset?confirm=RESET&_method=POST` | 405 |
  | `GET /__reset?confirm=RESET` | 405 |
- **校验位置**：`hard\app.py:1365` `if self.command != "POST"` —— `self.command` 由 `BaseHTTPRequestHandler` 从请求行直接取，**不读任何覆盖头/参数**，所以方法覆盖天然无效。

### 3.3 C3 · 裸路径变体（`//__reset` 等）【成功（orig）/ 失败（hard）】

- **证据**：`loop2-verify-supplement3-20261012-201334.json` 的 `C3_raw_path_attribution`（canary 判定），辅以 `loop2-verify-supplement-20261012-200845.json` 的 `fix3_path_variants` 与 `loop2-verify-pathprobe.py` 的解析实证。

| 路径 | orig | hard |
|---|---|---|
| `//__reset` | **200 · reset_triggered=true** | **405** · false |
| `/__reset` | 200 · true | 405 · false |
| `/__reset;` | **200 · true** | **405** · false |
| `/./__reset` | 404 · false | 404 · false |
| `/__reset/` | 404 · false | 404 · false |
| `/%5f%5freset` | 404 | 404 |
| `/__RESET` | 404 | — |
| `/__reset%00` | 404 | — |

- **为什么 orig 上 `//__reset` 能打中**：`urllib.parse.urlparse("//__reset").netloc == "__reset"`、`.path == ""`（`loop2-verify-pathprobe.py` 独立复现了这个解析行为），服务端按 path 路由时归一化成了 `/__reset`。`/__reset;` 同理被吃掉分号后缀。
- **hard 侧结论**：同一批裸路径在加固版上**全部 405/404，canary 未被动、审计零增长** —— 方法限制在路由归一化之后生效，所以路径花招绕不过 ① ② 层。**这条是加固的净收益，值得写进笔记**。
- **注意**：`//__reset` 的 405 出现在 `loop2-verify-20261012-200719.json` 的 `a6-hard-GET-path-doubleslash`，与 supplement3 互相印证。

### 3.4 E1 · A1 绕过（数量/溢出/竞态）【失败 · 阴性留证】

- **证据**：`loop2-verify-supplement5-20261012-201710.json` 的 `E1_A1_bypass`（11 例）+ `E1_A1_summary`（`any_negative=false`）。

| 用例 | payload | 状态 | 余额变化 |
|---|---|---|---|
| qty=0 | `product_id=1&qty=0` | **400** | 50000→50000 |
| qty=-1 | `product_id=1&qty=-1` | **400** | 不变 |
| qty=2147483648 | 32 位溢出 | **400** | 不变 |
| qty=100 | `29900*100=2990000 > 50000` | **400**（余额不足） | 不变 |
| qty=1e3 | 非整数 | **400** | 不变 |
| product_id=999 | 商品不存在 | **404** | 不变 |
| `product_id=1' OR 1=1--` | 注入尝试 | **404** | 不变 |
| 缺 product_id | `qty=1` | **404** | 不变 |
| qty 重复参数 | `product_id=1&qty=1&qty=100` | **200** | 50000→20100（**只下了一单 29900，取首值，非漏洞**） |
| 跨端点竞态 | 下单/提现同波 20 并发 | 200×10 / 400×10 | 50000→20100，无负 |
| 多会话并发 | 同用户 3 会话 30 并发 | 302×20 / 200×1 / 400×9 | 20100，无负 |

- **校验位置**：`hard\app.py:1005` `if qty < 1 or qty > 100:` → 400「数量无效」；`hard\app.py:1022-1025` 条件 UPDATE 兜住大额单；`hard\app.py:1011-1013` 服务端按 product_id 查价，不信任客户端 price。
- **一个未归因的观察**：多会话并发里出现 `302×20`（不是 400）—— 大概率是 3 个会话中 2 个被并发操作顶掉/未带 cookie 导致跳登录，**本轮未进一步验证**，记入 §4。

### 3.5 B1 / C6 · `check_write` 未覆盖的写入口（GET 仍能改状态）【成功 · 需处理】

- **证据**：`loop2-verify-20261012-200719.json` 的 `results.B.checks.b1_top_level_get_state_change`（hard:18096）+ `loop2-verify-supplement-20261012-200845.json` 的 `fix1_B1_get_state_change`（把 password 列纳入 state 比对）+ `loop2-verify-supplement3-20261012-201334.json` 的 `C6_uncovered_write_entries`。
- **实锤两条**：

| 入口 | 请求 | 状态 | 状态变更 |
|---|---|---|---|
| `/wallet/transfer` | `GET /wallet/transfer?to=bob&amount=7&csrf_token=<valid>` | **200「转账成功」** | alice 88800→88793，bob 100→107 |
| `/change-password` | `GET /change-password?new_password=zzz999&csrf_token=<valid>` | **200「改密成功」** | alice 密码 `alice123`→`zzz999` |

- **根因（源码位置）**：A2 只给四入口接了 `check_write`（`hard\app.py:997` order_create、`:1061` order_status、`:1105` coupon_claim、`:1150` wallet_withdraw —— 全库仅这 4 处调用），而 `wallet_transfer`（`hard\app.py:1185-1196`）只做了 `verify_csrf`、**没有方法限制**；`change_password`（`hard\app.py:1246-1254`）的 GET 分支只在 `not form.get("new_password")` 时渲染表单，一旦带上 `new_password` 就掉进写逻辑，而写逻辑只查 token 不查方法。
- **严重性口径**：跨站 CSRF 利用面被**收窄**（token 只在页面里出现，攻击者拿不到），但**没关死**——一旦有 XSS 或 token 泄露，GET 即可改密/转账，且顶级 GET 是 SameSite=Lax 也拦不住的导航类型。**判定：需处理，不应算 A2 完全达成**。
- 对照组：`/board`、`/upload` 的 GET 未改库（`db_changed=false`），`/wallet/transfer` 的 POST 无 token → 403（`t2-edgecases-20261012.json`：`transfer_none=403`）—— 说明加固方向对，只是漏了两个入口。

### 3.6 B2 / B3 / B4 · token 位置、改密后会话、Cookie 变形

- **B2 token 位置**（`results.B.checks.b2_token_location`，hard）：token 放 query → **200**（接受）；放 body → 200；query + JSON body → 200；**只放 `X-CSRF-Token` 头 → 403**（不读头）。根因：`hard\app.py:354-365` `form()` 把 query 与 urlencoded body 合并，不看 header。**token 可出现在 URL 里 → 会进访问日志/Referer，属信息暴露面**，判定**成功（可接受但设计偏弱）**。
- **B3 改密不轮换会话**（`results.B.checks.b3_session_after_password_change` + supplement2 `fix2_B3_session_after_pw_change`）：改密后 `sessions_row_still_present=true`、旧 Cookie `GET /home` → **200**、旧 Cookie 写请求 → **200**；同时 `login_with_old_password=200`（失败页）、`login_with_new_password=302`（成功）。**判定：成功（残余）**——口令变了但服务端会话行没删，这正是 hunt-session 的 Pattern 3「受害者以为改密就断了攻击者」的持久化 ATO 形态。**A4 只修了 logout，没修凭据变更**。
- **B4 Cookie 变形**（`results.B.checks.b4_cookie_variants`，hard）：`exact`→200、`quoted`（`"token"` 带引号）→**200**（`SimpleCookie` 会剥引号）、`upper`/`trailing_space`/`urlencoded`→302。**判定：失败（未绕过）**，但引号被规范化这一点值得记一笔。

## 4. 未验证项（不猜、不凑）

1. **Cookie 属性未取证**：本轮没有抓 `Set-Cookie` 的 `HttpOnly` / `Secure` / `SameSite` 属性，因此「跨站表单能否带上会话 Cookie」**未验证**。这直接影响 §3.1 / §3.5 的实际可利用性评估（若为 `SameSite=Strict`，浏览器侧会被拦；若缺失或 Lax，顶级导航仍可能带上）。
2. **D1 的真实浏览器验证未做**：现有证据是裸 socket 伪造头，不是真浏览器行为。真实浏览器一定会带 `Origin`（表单 POST），但本轮的硬证据只到"服务端不读这些头"这一步。
3. **8095 真实靶的 A6 未验证**：本轮硬性禁止对 8095 发起 `/__reset`，A6 结论全部来自沙箱 hard:18096（其 app.py 与 8095 哈希相同，可外推，但**未在 8095 上直接跑过**）。
4. **§3.4 多会话并发中的 `302×20` 未归因**：不清楚是会话被顶、cookie 未带还是别的原因。
5. **A1 的竞态窗口未做降并发测量**：只跑了 30 并发，未测 5/10/20 并发下的成功率曲线，无法给出"窗口有多宽"。
6. **D3 伪造来源头只测了 4 种**（`X-Forwarded-For` / `X-Real-IP` / 两者组合 / `Forwarded`）。四例都触发了复位，但**那是因为请求本身就来自回环**，不是头生效——结论只覆盖"这 4 个头不会被当成本地地址"，其它头（如 `Forwarded-Host`、`X-Client-IP`）未测。
7. **D4 非 urlencoded 承载 confirm 全 400**（multipart / text/plain / JSON / 无 Content-Type），只有 query 或 urlencoded body 能过 —— 但 `text/plain` 与 JSON 的 400 是因为 `form()` 不解析它们，**若将来 `form()` 支持 JSON，这条防线会失效**，未做前瞻验证。
8. **D5 multipart 打四入口**：`wallet_withdraw` / `order_create` 带与不带 csrf 的 multipart 全部 403、状态未变（阴性），但**只测了两个入口**，`order_status` / `coupon_claim` 未测。
9. **A5（绕过对抗专项）不在本档**：t2 报告 §4.1 明确 A5 归 t5，本报告不替它下结论。

## 6. 下一步建议

1. **优先修 §3.5（GET 写）**：给 `wallet_transfer` 与 `change_password` 补 `check_write`，或至少把方法校验抽成装饰器/统一入口，别再一个入口一个入口手工接。这是当前加固里**最容易再犯**的一类错（A2 已犯过一次）。
2. **§3.1（跨站复位）加一层上下文校验**：`Origin` 必须精确等于 `http://127.0.0.1:<port>`，**缺失也拒**；或走 t2 报告 §4.2 提的 `--reset` 启动参数路线，把 HTTP 路由彻底摘掉。同机场景下这条现在是真能打的。
3. **§3.6 改密轮换会话**：`change_password` 成功后 `DELETE FROM sessions WHERE user_id=?`（或至少删掉除当前会话外的所有行），对齐 A4 的做法。
4. **补 Cookie 属性取证**（§4.1）：抓一次 `Set-Cookie`，确认 `HttpOnly` / `SameSite`，否则 §3.1 / §3.5 的严重性评级悬着。
5. **A1 窗口测量**：降并发（5/10/20）跑一遍，给出成功率曲线，为后续报告写"复现条件"提供依据。
6. **交回 t5**：§3.1、§3.5、§3.6 三条都属于"绕过对抗"范畴，建议 t5 在 A5 里统一收口，别散落在本档。
